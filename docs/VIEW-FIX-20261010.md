## Causa y corrección

`ViewSubCommand` llama `toggleView`. El servicio crea un contenedor por UUID y
un timer de partículas cada tick, más un comprobador de duración cada segundo.
El constructor antiguo enviaba `sendActionBar` y `processTick` repetía ese envío
cada tick: hasta 20 avisos por segundo, incluso sin protecciones visibles.

PandaColors reconoce versiones cuyo número mayor es 1. Con `26.2`, la selección
alternativa extrae `.2`, inferior a 8, y termina en `NMS.Default.NMSMessageBuilder`.
Esta implementación ignora ACTION_BAR y usa `CommandSender.sendMessage`, enviando
al chat el texto configurado. La regresión ejecuta precisamente ese selector y
ese envío sobre una versión simulada de Leaf 26.2 y confirma el comportamiento.

Cambios en `ProtectionParticlesService.java`:

- El texto existente `Message.Protection.View.View-active-action-bar` se conserva
  y se envía al chat una sola vez, después de programar la activación. No se
  envía ningún mensaje durante los ticks. No se cambió la biblioteca global.
- Timer de visualización síncrono para evitar Bukkit fuera de su hilo y carreras
  sobre el HashMap con comandos, expiración y desconexión. La geometría, colores,
  selección de protecciones y envío de partículas permanecen iguales en fuente.
- Quit cancela y elimina inmediatamente el contenedor. Se guarda la identidad
  de Player de la sesión; una reconexión no hereda la vista anterior. Un callback
  de un contenedor viejo no puede cancelar el contenedor que lo reemplazó.
- Cambio de mundo refresca la ubicación/protecciones y reinicia el barrido usando
  la misma tarea, sin anunciar nuevamente ni renovar la duración.
- Stop limpia la referencia de tarea. Unload cancela vistas aunque falte el
  checker, elimina listeners y limpia el mapa. Reload reemplaza el checker.
- El cálculo de duración usa `1000L`, evitando desbordamiento entero.

Configuración leída por separado, idéntica para view en ambos nodos: radio 16,
velocidad 1.5, duración 60 segundos, mostrar ajenas false; permiso de view vacío,
cooldown 0; texto `&eProtection view: &aActive`. Se conserva ese texto sin
reescribir Lang.yml. El segundo comando desactiva; el siguiente vuelve a activar.

## /pb merge

Existe, alias `/pb m`, permiso configurado `protectionblocks.merge` en ambos;
para otras protecciones, `protectionblocks.merge.others`. Los permisos efectivos
individuales no se verificaron: no se indicó un jugador concreto. Ser miembro
puede mostrar candidatos, pero no basta para fusionarlos: se exige propietario
principal o permiso de otras protecciones, y ambas protecciones deben compartir
el UUID de propietario principal, incluso con el permiso administrativo.

| Ajuste actual | Custom | Sync |
|---|---|---|
| `Settings.Protection.Merge.Enabled` | true | true |
| `Settings.Protection.Merge.Must-be-close-for-merge` | true | true |
| `Settings.Network.View-only` | false | true |

Sync rechaza mutaciones mediante `checkIfWritable` y produce permiso denegado,
aunque merge esté habilitado. No se propone quitar este modo: forma parte de las
responsabilidades actuales del nodo.

Custom requiere mismo mundo, mismo propietario principal, protección no borrada
ni bloqueada (salvo bypass), jugador fuera de combate, permiso de comando y de
operación y evento de intento no cancelado. No admite fusionar consigo misma,
una descendiente que genere ciclo ni una protección ya fusionada al mismo padre.

La condición de cercanía usa intersección de cuboides inclusiva, **no distancia
ni adyacencia de bloques**. Un borde con coordenada exactamente igual puede
pasar; regiones con máximo X=10 y mínimo X=11 no pasan, aunque sus bloques sean
contiguos. El menú compara con el área del padre y la operación admite también
intersección con alguno de sus hijos, por lo que puede ocultar un candidato que
la validación final admitiría.

La operación enlaza hija/padre y hereda gestión/flags; no construye una región
nueva que rellene espacios entre áreas. Por eso decir simplemente que une
cualquier protección contigua sería incorrecto.

Además, hay un fallo preexistente en `/pb merge <padre> <hija>`: busca el padre
comparando su nombre o ID con **todos** los argumentos unidos, incluyendo el ID
de la hija. Normalmente termina en protección no encontrada. El autocompletado
también devuelve IDs mientras el filtro prefiere el nombre si existe. La ruta
sin argumentos abre el menú estando dentro de una protección elegible y evita
ese parseo; no salta permisos, geometría ni read-only. No se modificaron merge,
permisos ni configuración en esta entrega, ni se ejecutó ninguna fusión real.
